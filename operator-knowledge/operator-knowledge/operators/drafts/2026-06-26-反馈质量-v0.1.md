# 反馈质量 v0.1

状态：draft / 从样本中暂时收捻  
日期：2026-06-26  
来源：algo-coach 交互模式校准过程

## 背景

最初问题是：algo-coach 在算法学习中容易追问，但反馈感不足。

用户指出：算法题通常有明确标准，因此 agent 应该能告诉用户哪里对、哪里错、错在哪里、重要程度如何。

本 draft 从 102、230、199 三个样本里收捻“反馈质量”的偏好。

## 核心原则

反馈不是泛泛说“整体方向对”，而是要贴用户具体说法判断。

更好的顺序是：

1. 贴用户具体说法或伪代码；
2. 判断这个点对不对；
3. 指出具体错点；
4. 区分错误层级；
5. 必要时用一句话收束。

## 1. 不要用泛化肯定开头

负例：

```text
整体方向是对的。
你已经抓住了关键。
```

问题：

- 太模糊；
- 用户不论说什么都可以这样回复；
- 不够贴用户输入。

更好：

```text
你说“不能只沿着 right 指针走”，这个判断是对的。
你用“右子树优先访问，并且每层第一次遇到就记录”的思路，也是对的。
```

## 2. 可以先定性，但必须接具体依据

适用：

- 用户整体方向比较明确；
- 需要快速知道自己是不是走偏。

例子：102 层序遍历。

```text
整体思路是对的。

你抓住了核心：递归时带 layer，把节点值放进二维数组对应层。

主要问题是实现细节：

1. array[layer][-1] = tree.val 是覆盖最后一个元素，不是追加。
2. 新层创建条件要覆盖 layer = 0, array = []，所以 layer > len(array) 不行。
3. 如果从 layer = -1 开始并先判断，根节点会落在错误层级。
```

注意：

- 不需要再补“不是算法洞察问题”；
- 前面已经说明整体对和主要问题，结尾可省略。

## 3. 错误要分层，不要等权堆给用户

反馈时要区分：

- 核心洞察错误；
- 状态 / 变量语义错误；
- 递归组织错误；
- 边界条件错误；
- 实现细节错误；
- 表达 / 命名 / 笔误。

例子：199 右视图。

- “记录当前节点还是 `tree.right`”是核心伪代码错误；
- “是否覆盖”是规则语义错误；
- “右中左后序”命名不准确是次级表达问题；
- 示例编号写错是笔误。

## 4. “还没做”和“做错了”要分开

反馈质量里主要讲已经出现的错误。

如果某个点只是还没补齐，例如：

- 空节点边界还没写；
- 递归调用还没传参数；
- 提前停止还没处理；

它不一定和“写错了”同一类。

这些内容可以提示，但不要混入“错误的地方”列表里，避免用户以为所有问题都是同等错误。

## 5. 结构化要自然，不要像评分表

严格标题化可能太僵硬。

负向体验：

```text
你说得对的地方有：
...

错误的地方是：
...

另外：
...

总结：
...
```

问题：

- 像填表；
- 死板；
- 不像自然反馈。

更好：

- 保留对 / 错 / 次级问题 / 总结的逻辑；
- 但用自然段表达；
- 让结构藏在语言里。

例子：199 右视图。

```text
你这里有两个判断是对的：第一，右视图不能简单理解成一路沿着 right 走；第二，用右子树优先遍历，并且每层第一次遇到就记录，这个思路可以成立。

真正对不上的地方在伪代码。你说的是“记录这一层第一次遇到的节点”，但代码里写的是 tree.right，这就变成记录当前节点的右孩子了。

还有一个规则表述要统一：你说数组“可替换”，但模拟时其实是“这一层已经有值就跳过”。右视图这里应该按后者来，也就是每层首次写入后不覆盖。

“右中左后序”这个名字不准确；它更像右优先的前序遍历。示例里把右节点写成 2 属于笔误。

总体看，遍历策略是能成立的，主要是伪代码里“记录谁”和“是否覆盖”这两个点没对齐。
```

## 6. 边界解释要说明“停止对象”

例子：230 BST 第 K 小。

不够好的表达：

```text
if node.left == null: return num 这个边界不对。
没有左孩子不代表当前节点不用访问。
```

更清楚：

```text
递归停止条件应该是“当前没有节点可处理”，也就是 node == null。
node.left == null 只说明左子树为空，但当前节点本身仍然要被访问。
```

这里的关键是说清：

- 停止的是当前节点为空；
- 不是某个孩子为空。

## 7. 总结句可以有，但要按场景放

230 中用户希望有一句：

```text
总的来说，你已经抓住了“中序遍历计数”这个方向，
但递归函数里“什么时候计数、return 返回什么、何时停止”还没有分清。
```

但这句更适合放在具体问题之后，用作收束。

对 102 那种简单实现问题，结尾总结反而显得啰嗦，可以省略。

## 当前分流

```text
整体对 + 简单实现错
→ 简短定性 + 列具体实现问题，结尾可省略

洞察对 + 递归组织错
→ 说明已对方向 + 列组织问题 + 结尾一句收束当前卡点

策略对 + 伪代码和规则不对齐
→ 贴用户具体判断 + 指出规则和代码不一致 + 自然段总结
```

## 反例模式

### 1. 泛化肯定

```text
整体方向是对的。
你抓住了关键。
```

### 2. 包装式结尾

```text
当前距离完整逻辑已经很近。
```

如果前面已经列明问题，这类话通常没有必要。

### 3. 评分表式结构

```text
对的地方：
错误的地方：
另外：
总结：
```

结构有用，但不应僵硬。
