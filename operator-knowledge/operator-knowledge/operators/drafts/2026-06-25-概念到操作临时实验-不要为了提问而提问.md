# 概念到操作临时实验：不要为了提问而提问

状态：draft / 临时实验  
日期：2026-06-25  
目标：测试一个交互概念能否被转化为可执行规则，并观察这种转化是否真的改善 agent 输出。

## 1. 待操作化概念

不要为了提问而提问。

## 2. 当前概念含义

问题不是“agent 不能提问”，而是：

- agent 没有先处理用户已经给出的内容；
- 没有先给出正误反馈、缺口判断或重要程度；
- 为了保持苏格拉底式流程而机械追加问题；
- 追加的问题打断用户当前注意力轨道；
- 问题被悬挂后增加未解决空间。

## 3. 临时操作规则

当用户已经给出题解思路、伪代码、复盘或明确询问“对不对”时，agent 先执行反馈动作，而不是直接追问。

### 应做

1. 先给结论：
   - 对；
   - 部分对；
   - 错；
   - 尚不足以判断。
2. 指出依据：
   - 哪部分覆盖了核心结构；
   - 哪部分有漏洞；
   - 漏洞属于核心思路、边界条件、复杂度、实现细节还是表达问题。
3. 给影响：
   - 哪类用例会失败；
   - 是否会影响整体正确性。
4. 只有在确实需要推进理解时，才问一个问题。
5. 如果用户说“登记 / 记录 / 不用继续 / 下一题”，不追加追问。

### 不应做

1. 用户刚给出完整思路后，直接问下一个抽象问题。
2. 用户要求记录时，继续推进学习流程。
3. 总结后又追加多个新问题。
4. 为了不代笔而拒绝给正误判断。
5. 把“保护用户思考”误执行成“不提供标准反馈”。

## 4. 测试目标

本轮不是测试“agent 是否少提问”。

本轮测试：

> agent 是否能在用户已经给出思路时，先做有效反馈，再决定是否需要提问。

## 5. 样本

### 样本 A：207 课程表

来源：`records/2026-06-24-course-schedule.md`

用户给出了拓扑排序的自然语言流程，但混淆了：

- “所有已学课程”和“当前等待处理的课程”；
- 课程入队条件；
- 环判断时机；
- 反复扫描并删除边的实现风险。

期望新规则输出：

- 先判定“方向部分对”；
- 明确指出 4 个错误；
- 标记其中“集合语义混淆”和“过早入队”为核心正确性问题；
- 不应该立刻追问一个新问题，除非用于验证其中一个漏洞。

### 样本 B：102 层序遍历

来源：`records/2026-06-24-binary-tree-level-order-traversal.md`

用户使用递归 + layer + 二维数组的思路。

主要问题是实现细节：

- `array[layer][-1] = tree.val` 会覆盖，不是追加；
- 新层判断应是 `layer == len(array)`；
- 根节点应从 `0` 层开始；
- 左右孩子都传 `layer + 1`。

期望新规则输出：

- 先判定“整体思路对”；
- 把错误定级为“实现细节/边界表达”而不是核心思路错误；
- 用户问“有错误吗？没有错误，不要问我”时，不继续追问。

### 样本 C：230 BST 第 K 小

来源：`records/2026-06-20-kth-smallest-element-in-a-bst.md`

用户最初想到额外链表，后续理解中序计数，但伪代码把递归返回值和计数混在一起。

期望新规则输出：

- 先判定“核心方向已对，但代码组织还错”；
- 明确错误是“把中序遍历计数误写成子树节点数返回”；
- 指出统一边界应是 `node == null`；
- 只在必要时给一个小骨架，而不是连续追问。

## 6. 对照组与实验组

### 对照组：旧 algo-coach 规则

旧规则倾向：

- 追问优先；
- 不评价用户回答对错；
- 不直接揭示答案；
- 每轮只问一个问题。

风险：

- 正误反馈不足；
- 用户已给出内容仍被继续追问；
- 对有标准答案的算法题不够高效。

### 实验组：加入临时规则

新增倾向：

- 用户给出思路后，反馈优先；
- 问题只作为校验或推进工具；
- 用户要求记录或停止时，不追加追问。

## 7. 暂定观察维度

这些维度先不固化，只作为本轮观察：

| 维度 | 观察问题 |
|------|----------|
| 正误反馈 | 是否先说清楚对 / 部分对 / 错 |
| 错误定位 | 是否指出具体错点，而不是泛泛说“不严谨” |
| 重要程度 | 是否区分核心错误、边界错误、实现细节 |
| 提问必要性 | 是否只在必要时提问 |
| 聚焦性 | 是否围绕用户当前输入，而不是打开新分支 |
| 收捻 | 是否在反馈后停住或归并，而不是继续扩散 |

## 8. 临时成功标准

本轮不追求统计意义完整，只看是否出现明显方向性改善：

- 同一批样本下，新规则输出更能处理用户输入；
- 新规则减少无意义追问；
- 新规则没有变成直接代写答案；
- 用户负担下降；
- 输出仍然保留学习价值。

## 9. 待观察问题

- “反馈优先”会不会让 agent 过度给答案？
- “反馈优先”会不会退化成纯评价，缺少下一步引导？
- “不追问”会不会导致用户少了推导机会？
- 错误重要程度如何稳定判断？
- 是否需要正例/逆例成对写入 skill？
- 测试次数多少才足够判断稳定性？

## 11. 第一轮模拟观察

样本：207 课程表。

观察：

- 新规则相较旧规则，确实提升了正误反馈；
- 但新输出有退化为“纯评价”的风险；
- 它指出了问题，却没有继续引导用户应该往哪个方向修正或思考；
- 因此“不要为了提问而提问”不能被误写成“不要引导”。

修正方向：

- 反馈和引导应拆成两个正交维度；
- 先反馈，再给方向；
- 引导不一定表现为追问，也可以是：
  - 下一步只修一个核心漏洞；
  - 给一个最小反例让用户检查；
  - 指定当前应关注的变量语义；
  - 明确“先别管实现删除，先把队列语义分清”。

临时改写：

> 当用户给出思路时，agent 应先做正误反馈和错误定级；随后给出一个聚焦的下一步思考方向。只有当问题形式确实最适合推进时，才提出一个问题。

## 12. 实验方法修正：一次只测一个维度

用户指出：每轮最好只测试一个维度。

理由：

- 如果同一轮同时测试反馈、引导、聚焦、收捻等多个维度，结果很难解释；
- 输出变好或变坏时，不知道是哪条规则产生了影响；
- 为了保持正交性，应尽量采用单变量原则。

临时修正：

- 每轮只设置一个主测试维度；
- 其他维度可以作为备注观察，但不参与本轮结论；
- 下一轮若测试“反馈质量”，就暂时不评价“引导质量”；
- 若测试“引导质量”，则默认反馈规则已固定，不再同时调整。

## 13. 单维实验 1：反馈质量

测试目标：

> 用户给出算法思路后，agent 是否能清楚反馈：对不对、哪里错、错误重要程度。

不测试：

- 引导方向；
- 收捻；
- 等待；
- 术语负担；
- 是否继续提问。

样本：207 课程表。

结果观察：

- 对照组只粗略说“大方向对”，然后追问；
- 实验组能明确说“部分对”；
- 实验组指出对的部分、核心正确性错误、次级实现/判断风险；
- 用户认为“不错，符合”，但限定为“只是反馈上的话”。

临时结论：

- 在“反馈质量”单一维度上，反馈规则 v1 优于旧规则；
- 该结论不能外推到整体教学质量；
- 下一轮应固定反馈规则，只测试“引导方向”。

## 14. 实验方法修正：独立测试 vs 条件测试

用户指出：如果说“反馈质量已经达标，在此前提下测试引导方向”，这属于条件测试，不是正交独立测试。

需要区分：

- **独立测试**：单独测试某个维度本身，不把它建立在另一个维度达标的基础上；
- **条件测试**：在某个前置条件满足后，测试另一个能力是否继续改善结果。

当前修正：

- 后续实验记录必须标明本轮属于独立测试还是条件测试；
- 如果目标是保持正交性，应避免使用“在 XX 已经达标的前提下”这类表述；
- 条件测试可以做，但要单独标注。

## 15. 单维实验 2：引导方向（第一次尝试失败）

测试目标：

> agent 是否能给用户一个明确、聚焦、可执行的下一步思考方向。

用户反馈：

> 不好，这个试验组的输出。

当前状态：

- 实验组输出虽然给了 `queue / learned` 拆分；
- 也给了一个重跑例子的方向；
- 但用户认为输出不好；
- 需要继续分析失败点，不能直接判定实验组更优。

待分析问题：

- 是否仍然过度展开；
- 是否把“引导”写成了直接给方案；
- 是否没有贴合用户当前思考轨道；
- 是否把反馈维度混进了引导测试；
- 是否结尾仍然制造了额外任务压力。

## 16. 引导方向修正：需要给理由

用户指出：引导不只是告诉用户“接下来关注 XXX”，还需要说明为什么应该关注它。

有效引导至少应包含：

1. 看什么；
2. 为什么先看它；
3. 看它时只检查什么。

理由：

- 没有理由的引导容易变成指令；
- 给出理由才能让用户理解优先级；
- 也能减少 agent 随意指定焦点的问题。

临时结构：

```text
下一步先看 A。
原因是：A 决定/影响 B；如果 A 不清，后面的 C 会被带偏。
这次只检查 A 的一个表现：……
```

## 17. 单维实验 2：引导方向（修正版通过当前样本）

测试目标：

> agent 是否能给出有理由、聚焦、低负担的下一步思考方向。

不测试反馈质量。

样本：207 课程表。

修正版输出结构：

```text
下一步先看 array 的含义。

原因是：它不是变量命名问题，而是整个流程的状态问题。

如果 array 表示“所有学过的课”，旧课程会一直留在里面；
如果 array 表示“本轮刚学完、等待处理后继的课”，处理完这一轮后就应该替换成下一轮新入队的课程。

所以先别管删除 pre，也先别管怎么判断环。
这一轮只检查一件事：array 里的课程，在下一轮还会不会被重复当成“刚学完的课”使用。
```

用户反馈：

> 可以，这个很不错。

临时结论：

- 在 207 样本上，带理由的聚焦引导比直接给 `queue / learned` 方案更合适；
- 有效结构是：
  1. 下一步看什么；
  2. 为什么先看它；
  3. 暂时不看什么；
  4. 只检查一个表现。

注意：

- 这只是当前样本通过；
- 还不能证明该引导格式在所有算法题上稳定有效。

## 18. 实验阶段命名修正：方法校准 vs 正式测试

用户指出：当前仍在实验本身的构建阶段，不应把后续样本称为“复测”。

更准确说法：

> 用第二个样本继续校准实验方法。

当前阶段目标不是证明规则有效，而是检查：

- 实验设计是否能跑；
- 单一维度是否真的能被单独观察；
- 样本是否合适；
- 输出格式是否会误导；
- 记录方式是否能保留有用信息。

后续约束：

- 在方法未稳定前，少用“通过 / 有效 / 复测”；
- 只说“当前样本暴露了什么问题”或“当前样本下暂时可用”；
- 不能把方法校准阶段的观察包装成正式测试结论。

## 19. 102 样本负向标注

用户对 102 样本候选引导输出做出负向标注。

### 暴露的问题

1. **啰嗦**

   “别管 xxx 也别管 xxx”这种排除式表达不够好，会增加阅读负担。

2. **问题和引导不对齐**

   102 当前真实问题是：

   - 替换 vs 追加；
   - 初始化 / 新层创建条件。

   但候选引导转成了：

   - 第几层；
   - 数组第 n 个子数组。

   这导致引导从具体错误偏移到了另一个抽象层。

3. **控制感**

   “这一轮只检查一件事情”让用户感觉被控制，而不是被引导。

### 方法修正

- 引导必须贴合当前具体错误；
- 不要为了抽象统一格式而偏离用户正在处理的问题；
- 减少排除式表达；
- 少用任务分配式语言；
- “聚焦”不应表现为控制用户，而应表现为降低用户判断成本。

## 20. 102 样本正向改写

用户给出更合适的引导方式。

针对：

```text
array[layer][-1] = tree.val
```

更好的输出是：

```text
这表示替换这一层最后一个元素，不是加入。
你可以想想，怎么往一个数组中添加一个元素到尾巴中？
```

观察：

- 贴合具体错误；
- 不直接写出答案；
- 用一个很小的问题唤醒用户已有知识；
- 没有打开新分支；
- 没有控制感。

补充规则：

- 如果用户已说明“初始化部分我知道/只是懒得写”，agent 应该放行；
- 初始化判断这类简单细节，不应被机械追问；
- agent 应区分“用户不会”和“用户省略”。

## 21. 230 样本负向标注：不要先抛概念名词

候选引导中使用了：

```text
访问过程中的计数
子树递归返回的数量
```

用户指出：这类表达容易让用户不明所以。

问题：

- 用户不一定知道这些概念是什么意思；
- 用户也不知道自己伪代码中哪一部分对应这些概念；
- 用户可能只是随机探索写出了代码，并没有主动选择某种递归模型；
- agent 先抛概念名词，会增加理解成本。

方法修正：

- 先指用户原文中的具体位置；
- 再说这行实际在做什么；
- 最后才抽象成概念。

更像人类老师拿笔标注：

```text
你这里：left_num = cout(...) + 1
实际上是在把“左子树返回的结果”当成了当前节点的访问序号。
问题是：当前节点的访问序号不是由这一行天然得出的，而是要在“左子树处理完之后，访问当前节点”这一刻产生。
```

## 22. 230 样本正向改写反馈

改写方向：

- 先看用户代码中的具体行；
- 解释这一行实际表达了什么；
- 指出同一函数返回含义混乱；
- 最后用小问题聚焦 `cout` 的返回值。

用户反馈：

> 嗯，确实好很多。

有效点：

- 先指具体代码，降低抽象名词解码成本；
- 概念命名放在具体错误之后；
- 小问题聚焦在 `return` 含义，而不是打开新的递归讨论；
- 让用户能看到“自己写的哪一部分出了问题”。

关联新想法：

- 当前过程可能是一种偏好标注；
- skill / 资源包也许本质上不是知识压缩，而是偏好蒸馏；
- 后续可探索“偏好资源包”：把正例、逆例、修正理由、输出偏好沉淀为 agent 行为材料。

## 11. 第一轮样本运行：207 课程表

### 输入摘要

用户给出 `numCourses = 3`、`prerequisites = [[1,0],[2,0],[2,1]]` 的拓扑排序思路：

- 建立入度数组；
- 入度为 `0` 的课程进入数组/队列；
- 扫描 `prerequisites`；
- 如果依赖的第二个元素存在于 array，就减少对应课程入度；
- 入度变为 `0` 时加入 array；
- 删除对应边；
- 若没有新入度为 `0` 的元素，判断存在循环。

### 对照组：旧规则倾向

旧 `algo-coach` 可能会输出：

```text
你的大方向是对的，已经抓住了入度数组 + 当前可学习课程集合 + 消除依赖这条主线。

我追问你一个关键问题：

在你的流程里，array 到底表示“所有已经学过的课”，还是“当前这一轮刚刚要处理的课”？这两个含义你准备怎么区分？
```

### 对照组观察

优点：

- 问题确实指向核心漏洞；
- 没有直接代写完整解法。

问题：

- 虽然开头说“大方向对”，但反馈密度不足；
- 用户输入中已经存在多个明确错误，但旧规则只挑一个问题追问；
- 没有给出错误重要程度；
- 没有说明“课程 2 过早入队”这个具体错误；
- 用户可能不知道自己的方案到底是“局部细节错”还是“核心机制错”。

### 实验组：反馈优先规则

新规则期望输出：

```text
部分对。

你抓住了核心方向：用入度数组记录每门课剩余先修数量，并从入度为 0 的课程开始消除依赖。

但当前方案有两个核心正确性问题：

1. array 的语义混了
   它现在既像“所有已经学过的课”，又像“当前这一轮要处理的课”。
   如果后续继续用 array 判断 `pre[i][1] in array`，旧课程会反复参与消除依赖。

2. 课程 2 被过早加入
   在 `[[1,0],[2,0],[2,1]]` 中，课程 2 的入度一开始是 2。
   处理 `[2,0]` 后，课程 2 的入度只会从 2 变成 1，还不能入队。
   必须等 `[2,1]` 也被处理后，入度变成 0，才能加入队列。

还有两个实现风险：

3. “没有新元素变 0”不能立刻判环
   真正判环条件是：队列已经空了，但仍有课程没完成。

4. 遍历 prerequisites 时同步删除边容易跳过元素
   这属于实现细节风险，不是核心算法概念错误。

所以结论是：拓扑排序方向对，但队列语义和入队时机需要修。
```
